## 設計の考え方
(
- プロセス中心（POA） — 業務の流れ（処理）から考える。DFDで描く
+* データ中心（DOA） — **データは一番安定した資源**。データ構造から考える
- オブジェクト指向 — データと処理をセットの部品にする
)
| DFDの記号 | 意味 |
| □ | 源泉・吸収（外部） |
| ○ | プロセス（処理） |
| ＝ | データストア |
| → | データフロー |
! DFDには処理の順番や条件分岐は書かない。書くのはデータの流れだけ
+ DFDでのモデル化の順番 — 現物理 → 現論理 → 新論理 → 新物理（今を抽象化してから新しくして具体化）

## オブジェクト指向
(
-* カプセル化 — 中身を隠す。中を変えても外に影響しない
- クラス／インスタンス — ひな形／実体
-* 継承（インヘリタンス） — 親の属性・メソッドを子が引き継ぐ。差分だけ書けばいい
- 汎化（is-a） — 「自動車 is-a 乗り物」。共通部分を親クラスに
- 集約（part-of） — 「エンジン part-of 自動車」
+* 多相性（ポリモーフィズム） — 同じメッセージでも相手によって動作が違う（実行時に決める＝動的結合）
+ 抽象クラス — 中身のないメソッドを持つ。**インスタンスを作れない**
+* オーバーライド — 親のメソッドを子で上書き
+* オーバーロード — 同じクラスで同じ名前・違う引数
+ 委譲 — 自分の仕事を他のオブジェクトに頼む
+* デザインパターン — よくある設計問題の解き方の型（GoF：生成・構造・振る舞い）
+ Observer — 状態が変わったら依存先に通知。Singleton＝インスタンス1個だけ、Adapter＝変換役をはさむ
)

## UML
| 図 | 何を描く |
| クラス図 | クラスと静的な関係（多重度・汎化・集約） |
| ユースケース図 | 利用者（アクタ）から見た機能 |
+| シーケンス図 | メッセージのやり取りを**時間順**に |
+| コミュニケーション図 | オブジェクト間の**つながり**重視 |
+| アクティビティ図 | 処理の流れ。**並行処理**も書ける |
+| 状態マシン図 | 1つのオブジェクトの状態遷移 |
( クラス図の記号
+ △（白三角） — 汎化（親の側に付ける）
+ ◇（白ひし形） — 集約（全体の側）。部品は全体が消えても残る
+ ◆（黒ひし形） — コンポジション。全体が消えたら部品も消える
+* 多重度 — 1・0..1・0..*・1..*。**相手1つから見た自分の数を、自分の側の端に**書く
)
> 社員—年（入社年）：社員側は「0..*」（入社ゼロの年もある）、年側は「1」（入社年は1つ）

## モジュール分割
(
+ STS分割 — 入力（源泉）・変換・出力（吸収）に分ける
+ TR分割 — トランザクションの種類で振り分ける
+ 共通機能分割 — 共通する機能を1つにまとめる
+ ジャクソン法 — **出力**のデータ構造から決める。ワーニエ法＝**入力**のデータ構造から
)
> 結合度は低く、強度は高く（外とのつながりは弱く、中のまとまりは強く）
@lad モジュール結合度（つながりの強さ）| 悪い（強く結合） | 良い（独立）
内容結合 :: 相手の中身に直接アクセス・ジャンプ
共通結合 :: 共通領域の**データ構造**を共有
外部結合 :: 共通領域の**データ項目だけ**共有
制御結合 :: 相手の動きを決める引数を渡す
スタンプ結合 :: データ構造を**引数**で渡す
+データ結合 :: 必要なデータ項目だけを**引数**で渡す（最良）
@end
@lad モジュール強度（中のまとまり）| 悪い | 良い
暗合的強度 :: 関係ないものを適当にまとめた
論理的強度 :: 関連する機能を引数で選んで実行
時間的強度 :: 初期化など同じ時点の処理をまとめた
手順的強度 :: 順番に実行する処理をまとめた
連絡的強度 :: 順番＋データの受け渡しあり
情報的強度 :: 同じデータ構造を扱う機能をまとめた
+機能的強度 :: 1つの機能だけ（最良）
@end

## テスト
@fig vmodel | V字モデル | 左で決めたことを同じ高さの右で確かめる。「暫定的な」テスト要件を決めるのはソフトウェア方式設計
(
+ 運用テスト — 本番（準本番）環境で**利用者・運用者**が主体。開発プロセスじゃなく運用プロセス
+ 共通フレーム — 発注者と開発者の「共通の物差し」{{06-3}}
)
( テストケースの作り方
- ブラックボックス — 仕様（入力と出力）だけ見る。冗長なコードは見つけられない
- ホワイトボックス — 中の構造（分岐）を見る
-* 同値分割 — 有効・無効のグループから代表値を1つずつ
-* 限界値分析 — **境界の両側**（0〜100なら −1, 0, 100, 101）
+ 原因結果グラフ — 原因と結果の関係を図に→決定表でテストケース
)
| 網羅 | 条件 | A AND B なら |
| 命令網羅 | 全命令を1回以上 | 真の1ケース |
| 分岐（判定条件）網羅 | 判定の真・偽を両方 | 真真・真偽 |
+| 条件網羅 | 個々の条件の真・偽を両方 | 真偽・偽真（判定は偽のまま） |
+| 複数条件網羅 | 条件の真偽の全組合せ | 4ケース |
! 条件網羅は分岐網羅を含まない。強さは 命令 ＜ 分岐 ＜ 複数条件
= #+ テストの計算
= サイクロマティック複雑度 ＝ 辺 − 節点 ＋ 2 ＝ 判定の数 ＋ 1
= エラー埋込み法： 見つけた埋込み ÷ 埋込み総数 ＝ 見つけた真のエラー ÷ 真のエラー総数
=   例）48個埋込み→36個発見、真のエラー42個発見 → 総数56 → 残り14個
= 2段階エディット法： 総エラー数 ＝ N_A × N_B ÷ N_AB
(
+ 信頼度成長曲線（ゴンペルツ曲線） — 累積バグ数のS字。**水平になるまで**テストを続ける
+ テストカバレージ分析 — 実行された経路の割合（網羅率）を測る
+ プロファイラ — どこが遅いか（ボトルネック）を調べる
+ スナップショット — 埋め込んだ所でレジスタ・メモリを出力
)
@mx 結合テストの仮モジュール
x: トップダウン（上から結合） | ボトムアップ（下から結合）
y:  |
TL: スタブ :: まだない**下位**の代役。値を返すだけ
TR: ドライバ :: まだない**上位**の代役。呼び出すだけ
BL: 上位モジュールの信頼性が高い :: 何度もテストされるから
BR: 下位は並行してテストできる :: でも上位の問題が最後に見つかる
@end
(
+ ビッグバンテスト — 一気に全部つなぐ。原因が特定しにくい
+* 回帰テスト（リグレッション） — 変更後、**他に影響が出てないか**確かめる
)

## 品質とレビュー
( JIS X 25010 製品品質（定義文のキーワードで判定）
+ 機能適合性 — ニーズを満たす**機能**
+* 性能効率性 — 使う**資源の量**に関係する性能
+ 互換性 — 他と**情報交換**・共存できる
+ 使用性 — 使いやすさ（アクセシビリティ含む）
+* 信頼性 — 明示された**時間帯**に機能を実行できる
+ セキュリティ — 権限に応じてデータを守る
+* 保守性 — **修正**しやすい
+ 移植性 — 別の環境に**移せる**
)
( レビュー
+* ウォークスルー — **作成者**が説明しながら進める
+* インスペクション — **モデレータ**が仕切る公式レビュー。記録と追跡あり
+ パスアラウンド — 成果物を回覧して個別に見てもらう
+ ピアレビュー — 同僚と。IV&V＝開発と独立した組織が検証
)
! レビューの目的は誤りを見つけること。**作成者の人事評価には使わない**

@ch 04-2 | ソフトウェア開発管理技術 | どんな順番で作り、どう直し、組織の実力をどう上げるか
@map
flow: 作る順番::ウォータフォール〜アジャイル > +アジャイルの道具::XP・スクラム > 直す・使い回す::保守の4タイプ > 組織の実力::CMMI
アジャイル用語（スプリント・レトロスペクティブ・テスト駆動）は近年毎回出る。
@end
| モデル | 進め方 |
| ウォータフォール | 上流から下流へ一方向。戻らない |
+| スパイラル | 部分ごとに工程を繰り返す。**リスク最小化** |
+| インクリメンタル | **最初に全体の要求を決めて**、分けて順に作る |
+| 進化的 | 要求があいまいな前提で、繰り返しながら洗練 |
| プロトタイピング | 試作品で要求をはっきりさせる |
! インクリメンタル（要求は最初に確定）と進化的（要求があいまい）の取り違え

## アジャイル
(
- アジャイル — 短い期間（1週〜1か月）の反復（イテレーション）で、変化に柔軟に対応
+ タスクボード — ToDo／Doing／Done
+* バーンダウンチャート — 縦軸に**残作業量**、横軸に時間
)
( XPの5つ
+ ペアプログラミング — 2人1組。書く人＝ドライバ、助言する人＝ナビゲータ（交代しながら）
+* テスト駆動開発 — **テストを先に書いて**、通る最小限のコードを書く
+* リファクタリング — **外から見た動きは変えず**に中を書き直す→回帰テスト
+ 継続的インテグレーション — 結合とテストをこまめに繰り返す
+ コードの共同所有 — 誰のコードでもチーム全員が直せる
)
@flow +スプリントプランニング::やることを選ぶ > デイリースクラム::毎日の短い朝会 > +スプリントレビュー::成果物を見る > +スプリントレトロスペクティブ::進め方をふりかえる || スクラム：1スプリント＝1〜4週間で繰り返す
(
+* プロダクトオーナ — プロダクトバックログの**優先順位**を決める
+ スクラムマスター — チームを支援して障害を取り除く（命令はしない）
+ ベロシティ — 1スプリントでこなせた量
+ ユーザストーリー — 「〜として、〜したい。なぜなら〜」
+ モブプログラミング — 全員で1台
+* DevOps — 開発と運用が協力して、自動化で素早く出し続ける。CI/CD
+ リーン開発 — ムダをなくす7原則
+ ローコード — GUIでほぼコードを書かずに作る
)
! ペアプロの「ドライバ」（書く人）と結合テストの「ドライバ」（仮の上位）は別物

## 再利用と保守
(
+* リバースエンジニアリング — 既存のソフトから**仕様を導く**（逆向き）
+ マッシュアップ — 複数のAPIを組み合わせて新サービス
)
@mx 保守の4タイプ（JIS X 0161）
x: 問題・障害に対応（訂正） | 良くする（改良）
y: 起きてから | 起きる前に
TL: 是正保守 :: 見つかった問題を受け身で直す
TR: +適応保守 :: **環境の変化**（OS更新など）に合わせる
BL: +予防保守 :: 潜在的な障害を**運用障害になる前**に直す
BR: +完全化保守 :: 故障として現れる前に直す・改良する
@end
@stack CMMI（組織の成熟度）
1 初期 :: 場当たり。人に依存
2 管理された :: 似たプロジェクトなら繰り返せる
+3 定義された :: **標準プロセス**がある
+4 定量的に管理された :: **数字で**管理・予測できる
5 最適化している :: 継続的に改善し続ける
@end
